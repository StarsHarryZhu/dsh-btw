# AGENTS.md

## 1. Role

dsh-btw is a DeepSeek Harness plugin for side questions. Typing `/btw <question>` (or choosing "Ask" on text selected in a reply) asks a separate, cheap model a one-off question about the current conversation without interrupting the main agent. The answer appears in a card in the conversation: a spinner while it works, then a model-written title, the Markdown answer, and its web sources. A card collapses to its title and can be deleted; the right sidebar lists every live card of the session. The plugin replaces `@michengai/dsh-btw`, whose forked subagent replayed the main agent's tool-call history with no tool declarations, so the model kept calling tools it did not have.

## 2. Constraints

- Never send a request that carries tool-call history without declaring those tools. The main conversation reaches the side model only as flattened text (`src/host/transcript.ts`); the only declared tool is `web_search`; the final request after the step cap carries no tools and no tool blocks.
- Follow Claude Code's `/btw` safeguards: a reminder that the side model cannot act, a denial for any other tool name, a hard step cap, and a readable fallback when the model only tried to call tools.
- No reasoning text ever reaches the card; reasoning blocks are kept only for adapter replay inside one run.
- Every side question lives in the Session log as command records (`/btw`, `/btw-quote`, `/btw-answer`, `/btw-delete`); the client keeps no shared state beyond per-browser collapse preferences.
- Question commands return immediately; the host half records the answer later through `/btw-answer`, so the composer is never held.
- Runtime imports are limited to `@deepseek-ai/cordis` and `@deepseek-ai/schemastery` (host, declared as peers) and the page's shared modules `react`, `react/jsx-runtime`, `react-dom`, `@deepseek-ai/dsh-client-ui-primitives` (browser). Host types are structural.
- Package identity: `dsh-btw` version `0.1.0`, shown as `dsh-btw` on the Plugins page; `engines.dsh` is `>=0.2.1-rc.1` with no upper bound. `tests/manifest.test.ts` pins all three.
- Default model is `deepseek-account` / `deepseek-flash` at `low` effort; the settings page can pick another model or follow the session's model.
- `lib/` is generated by `node build.js` and committed; never edit it by hand.
- Text-only for now: no interactive UI plugins render inside cards.

## 3. Contents

- `src` — plugin source: host half, browser half, shared protocol.
- `tests` — vitest specs for both halves and for this documentation set.
- `scripts` — development helpers.
- `locale` — display name and description for the Plugins page.
- `lib` — generated build output that a profile loads.
- `build.js` — type-check, emit the host half, bundle the browser half, and self-check the bundle.
- `cordis.patch.yml` — the bundle layer inserting the `dsh-btw` row.
- `package.json` — package manifest with the `dsh` bundle and client fields.
- `tsconfig.json` — host type-check configuration.
- `tsconfig.build.json` — host emit configuration.
- `tsconfig.client.json` — browser compile configuration.
- `vitest.config.ts` — test runner configuration.
- `README.md` — user-facing overview and install steps.
- `.gitignore` — ignored build residue and local notes.

## 4. Progress

- Done: host runner with flattened history, web search, denial, step cap, and fallbacks; four commands with immediate return and deferred `/btw-answer`; inline cards with spinner, title, collapse, copy, delete; cards under quoted replies; selection bar with ask and add-to-conversation; sidebar history tab with locate; settings page for model source, model, effort, and search rounds; build self-check and tests.
- Verified in the real web app (dsh web from the 0.2.1-rc.2 checkout, deepseek-account / deepseek-flash): direct answers from flattened history with no tool attempts, a refusal in text when asked to read files or run commands, web search with sources, pending spinner, collapse surviving reload, deletion surviving a server restart, quote cards under the quoted reply, add-to-conversation, sidebar history with locate, settings save to the profile patch, and a `/btw` sent while the main turn runs (not folded into it).
- Open: a `/btw` sent right after a main prompt can appear above that prompt, because the host logs the command before the prompt's message event.
- Known limits: deletion hides a card everywhere but the log keeps its events; history only covers the loaded part of the conversation; a card stays pending if the host restarts mid-answer until it is marked interrupted after the timeout.
- Goal later: render interactive UI plugin output (for example dsh-intelligent-UI) inside cards through a `tool.result.<tool name>` factory convention.
